Endpoint Detail — Example
POST /api/ai/tutor

Get an AI-powered explanation for a quiz question the student answered incorrectly. Uses Claude with temperature=0 for deterministic responses.

Authentication

Requires an active user session. Rate limited to 10 requests per minute per user.

Request Body
TypeScript — Zod Schema 
const TutorRequestSchema = z.object({
  questionId: z.string().uuid(),
  questionText: z.string(),
  selectedAnswer: z.string(),
  correctAnswer: z.string(),
  rationale: z.string().optional(),
})
Response
JSON — 200 OK 
{
  "explanation": "The Colosseum uses the system of...",
  "keyTakeaway": "Remember: superimposed orders...",
  "relatedTopics": ["ALE-HIST-001-06"]
}
Example
curl 
curl -X POST /api/ai/tutor \
  -H "Content-Type: application/json" \
  -H "Cookie: sb-session=..." \
  -d '{"questionId":"...","questionText":"...","selectedAnswer":"A","correctAnswer":"B"}'

Architecture Overview

System design, database schema, authentication, data flow, and deployment for SlateCamp.

Database Schema

SlateCamp uses PostgreSQL via Supabase with 50 tables, 89 RLS policies, 31 triggers, and 13 custom enums. The schema is organized into 5 domain clusters.

Cluster 1 Taxonomy & Content
disciplines → name, acronym, passing_threshold_pct
taxonomy_tree → level, name, ale_id, node_type, bloom_level, difficulty
questions → text, options (JSONB), correct_option_id, topic_id → taxonomy
wiki_articles → title, slug, content (MDX), status, hero metadata
wiki_article_taxonomy → article_id ↔ node_id junction, is_primary
wiki_ei_prompts → prompt_text, reveal_text, options, insert_after_heading
models_3d → name, url, supported_phases
spatial_hotspots → model_id, position_xyz, phase
Cluster 2 Quiz Engine
quiz_sessions → user_id, test_mode, status, question_ids[], config
user_interactions → session_id, question_id, is_correct, time_spent_ms Immutable
Cluster 3 Mastery & Scoring
user_node_mastery → mastery_weight (EMA), next_review_at, ease_factor
user_mastery_history → mastery_weight snapshots with reason
user_global_stats → global_readiness_score, sub_scores, streaks
readiness_score_snapshots → score, sub_scores, is_proof_simulation Append-only
blindspot_queues → node_ids[], status (generated by cron)
Cluster 4 Trails & Progression
camp_trails → name, trail_type, intensity, duration_days
trail_days → trail_id, day_number, estimated_minutes
trail_steps → step_type, target_node_ids[], question_count
user_trail_enrollments → trail_id, status, current_day, streaks
Cluster 5 Identity & Billing
profiles → full_name, discipline_id, reviewer_type, account_mode
user_subscriptions → tier, status, stripe_subscription_id, payrex_id
organizations → name, type, max_seats
user_roles → role (super_admin | content_admin | sme_reviewer)
audit_logs → actor_id, event_type, table_name, content_snapshot

Authentication & Authorization

Core Data Flow — Mastery Loop

Every student action feeds a closed-loop mastery engine. This is the core system that powers the Readiness Score, Taxonomy Heatmap, and all progression features.

System Flow
// The Mastery Loop — every table exists to serve this

Student Interaction (quiz answer, wiki read, 3D Lab)
  → user_interactions          // immutable event log
  → user_node_mastery          // EMA weight, updated via trigger
  → Readiness Score + Heatmap  // always current
  → Progression responds       // Blindspot, Endurance, Proof, Trail
  → Student returns tomorrow
