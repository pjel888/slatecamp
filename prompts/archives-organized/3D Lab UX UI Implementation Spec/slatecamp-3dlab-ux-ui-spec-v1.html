Chapter 01 UX Research Foundation
Why does 3D learning exist in SlateCamp at all? Before building a single component, every decision must be anchored to what research tells us about how architecture students learn spatial concepts — and where 2D methods fail them on the ALE.
The core learning science case
Why 2D fails architecture students on the ALE Dual Coding Theory + Spatial Cognition Research
Research
Dual Coding Theory — Paivio (1986)
Information encoded through both verbal AND spatial channels simultaneously is retained 65% better than information encoded through only one channel. A wiki article about stairway rise-run ratios is verbal only. A 3D stairway model the student can rotate and measure is spatial + verbal simultaneously.
Mayer's Multimedia Learning Principle
Words + pictures consistently outperform words alone — not because visuals are "nicer" but because they activate a separate cognitive processing channel. The 3D Lab is not a feature enhancement. It is a fundamental encoding mechanism for spatial content.
Situated Learning — Lave & Wenger (1991)
The most effective learning happens when the student is doing something that mirrors the real-world task. Manipulating a 3D ramp model where the slope turns red when it exceeds BP 344 limits is situated learning. Reading the slope value in a table is not. The ALE Area C tests situated spatial judgment — the 3D Lab trains exactly that.
3D is required for: stairway geometry, ramp slopes, accessible toilet clearances, egress travel paths, structural bay spans, setback relationships, and any content where the spatial relationship between elements is the testable concept.
3D is not required for: occupancy classification tables, code penalty amounts, date-based facts, procedural sequences. Use 2D or prose for these.
The governing test: "Would a 2D diagram explain this equally well?" If yes, build the 2D. 3D only earns its place when spatial understanding is the learning objective.

Cognitive load rules specific to 3D learning
Mayer's principles — violations to never buildEach violation reduces learning, not just aesthetics
Do — increases learning
Segmenting: Let students control pacing. Never auto-play through hotspots.
Spatial contiguity: Labels appear adjacent to what they describe. Never in a sidebar legend.
Signaling: Highlight only the element relevant to the active hotspot. Dim others.
Pre-training: The linked wiki article is read before the 3D model is opened.
Personalization: Hotspot text is conversational — "Notice that the turn radius here is…" not "The minimum dimension is…"
Don't — reduces learning

Auto-advancing guided tours with no pause — violates segmenting principle
Text in hotspot that exactly repeats the label — redundancy violation
More than 5 active hotspots simultaneously — visual overload
Decorative geometry that doesn't serve the learning objective — extraneous material

Chapter 02 UX Principles & Design Intent
The 3D Lab must feel like a training tool in a focused studio — not a game, not an app demo, not a tech showcase. The interaction design follows five principles that govern every decision.
①
Spatial first, data second
The model speaks before the numbers do. Hotspots reveal data after the student has oriented themselves in the 3D space. Never lead with a data table inside a 3D viewer.
②
Student controls the pace
No auto-rotate on load. No forced guided tour. No time pressure. The student explores, the model responds. Pace is always in the student's hands.
③
Calm visual environment
Cream background, soft directional lighting, no particle effects, no dramatic fly-through animations. The ALE is stressful enough. The 3D Lab is a focused workspace.
④
2D when it works
Hotspot info panels, question overlays, tool palettes, and onboarding are all 2D HTML over the 3D canvas. The 3D viewport is for spatial understanding. Everything else is flat UI.
⑤
Every hotspot earns its place
A hotspot exists only if it teaches something the model's geometry alone cannot convey. If a student can read the dimension from looking at the model, the hotspot is optional, not required.
⑥
One question per interaction
After engaging with a hotspot, the student can answer one exam question about that specific element. Not a quiz session. One question, one answer, one rationale. Then back to exploration.
The 3D Lab mental model to design for

Think of the 3D Lab as a physical scale model on a studio table. The student walks around it, crouches down to look at a detail, picks up a dimension guide, reads a code annotation on a sticky note. They are not "playing a game" — they are studying a physical object. The UI should feel like the tools on that studio table: functional, precise, calm, professional. The hotspot dots are the sticky notes. The info panel is the code annotation card. The question button is the practice exam question written on the back of the card.

Chapter 04 Hotspot System — Dots, Info Panels & Question Overlays
The hotspot is the primary learning interaction in the 3D Lab. This chapter defines every state, every visual, every piece of copy, and every transition for the complete hotspot interaction flow: dot → info panel → question → answer → rationale → back to model.
Hotspot dot — three types, three colors
Dot types and their semantic meaningColor encodes meaning — never decorative
Cobalt — Informational
Explains a dimension, provision, or spatial relationship. No right or wrong. Pure learning.
Gold — Exam-critical
A specific value the ALE has historically tested. The most important hotspot in the model.
Red — Violation marker
Used in violation-mode models only. Marks an element that fails code compliance. Not a default state.
Usage constraint
Maximum 5 hotspot dots visible simultaneously. If a model has more than 5 hotspots, use a category filter system (see Chapter 06) to show one category at a time. Showing all hotspots simultaneously creates extraneous cognitive load and reduces the learning value of each one.
Dot visual specificationExact dimensions, animations, states
Default (idle) state: 18×18px circle. Fill = type color. Border 2.5px solid white. Outer pulse ring: 6px, same color at 30% opacity, animated slow pulse (2s ease-in-out infinite). CSS scale(1).
Hover state: Scale to 1.25 via CSS transform (200ms ease). Pulse ring expands to 10px. Cursor: pointer.
Active (clicked) state: Scale 1.15. White border becomes 3px. A thin connecting line (0.5px, dashed, type color) runs from the dot to the info panel. The associated model geometry highlights (tint overlay).
Visited state: Same as idle but pulse ring stops animating. A small checkmark (✓) appears at bottom-right of the dot circle. This tells the student "you've already seen this one."
distanceFactor on Html component: Set to 8. This ensures the dots maintain consistent screen size regardless of camera zoom — they don't grow huge when the student zooms in.

Panel width: 240px. Fixed width. Never wider. On mobile, the panel anchors to the bottom of the screen as a drawer (not a floating card).
Panel position: Appears adjacent to the clicked hotspot dot, preferring right-side placement. If the hotspot is in the right half of the viewport, the panel opens to the left. Always keeps 16px clear of viewport edges.
Eyebrow (DM Mono 9px): Format: "[Element type] · [Source section]". For gold hotspots: "Most-tested · ALE Watch" in gold color.
Title (Inter 13px, 600wt): Name of the specific element. Short noun phrase. Never a sentence.
Body text (Inter 12px, 400wt): 2–3 sentences max. Conversational voice — explains the spatial relationship and the "why" behind the dimension. Never starts with "The minimum is…" — leads with the concept, ends with the value.
Values table: 2–3 rows max. Always shows the 2024 correct value first. If a 2013 value changed, show the old value with strikethrough below it in muted color.
Source line (DM Mono 10px): Full section reference. Never abbreviated.
Practice CTA: Always present. "Practice a question on this →". Opens the question panel (see below). Never says "Take a quiz" or "Test yourself" — framing is deliberate practice, not assessment.
Close: Click anywhere outside the panel OR click the dot again. No explicit close button needed — the behavior is natural.

Panel width: 280px. Wider than info panel because question text + 4 options require more horizontal space.
Panel position: Replaces (not stacks with) the info panel. Smooth transition — the info panel fades out as the question panel fades in. Same screen position.
Question: Exactly 1 question per hotspot. Never 0, never 2. The question must test the specific dimension or provision shown in the info panel. It is not pulled from a random pool.
Options: Always exactly 4. One correct. Three plausible distractors — including the 2013 superseded value where applicable (most-tested misconception pattern).
Answered state: All options lock immediately. Correct option gets green background. Wrong option (if chosen) gets red. The rationale appears inline below the options — never on a new screen.
Rationale: 2–3 sentences. Explains why the correct answer is correct AND why the most-common wrong answer is wrong. Inline in the panel — no navigation required.
After rationale: "← Back to model" link below the rationale. Closes the question panel and returns focus to the 3D canvas. The hotspot dot gets a ✓ visited state.
Score tracking: Correct/wrong is recorded to the student's heatmap node for this topic. Silent — no score announcement in the panel. The heatmap updates in the background.
Complete hotspot interaction flow — state machine
1
Model loads — dots visible, idle pulse
All hotspot dots are visible. Cobalt/gold/red according to type. Slow pulse animation draws attention without demanding it. Student can orbit the model before clicking anything.
State: IDLE · Transition: onClick dot
2
Student clicks a hotspot dot
Dot scales to active state. The associated model geometry receives a cobalt tint overlay. The info panel fades in (150ms ease-out) adjacent to the dot. Camera does NOT automatically move — student controls camera.
State: INFO_OPEN · Transition: onClickCTA "Practice a question"
3
Student reads info panel
Info panel is visible. Student reads the explanation, sees the value, optionally rotates the model to view from a different angle. The info panel stays open during camera movement.
State: INFO_OPEN · Transition: tap outside = IDLE, tap CTA = QUESTION_OPEN
4
Student taps "Practice a question on this →"
Info panel fades out. Question panel fades in (same position, 150ms). The 3D canvas dims slightly (background overlay at 20% opacity) to signal that a focused task is active. Camera orbit is temporarily locked while the question is open.
State: QUESTION_OPEN · Transition: onSelectOption
5
Student selects an answer
All options lock immediately. Correct option highlighted green. Student's choice highlighted (green if correct, red if wrong). Rationale appears inline. No sound, no animation celebration. Just the information.
State: ANSWERED · Transition: onClickBackToModel
6
Student taps "← Back to model"
Question panel fades out. Canvas background overlay lifts. Camera orbit re-enables. Hotspot dot receives ✓ visited mark. Heatmap node updated silently in background. Student is back to the free-explore state.
State: IDLE · Transition: free exploration or next hotspot

Chapter 06 Parametric Controls — Sliders, Inputs & Panel Design
Parametric modules (Stairway Configurator, Ramp Slope Visualizer) allow students to adjust code variables and see the model update in real time. This is the highest-value interaction in the 3D Lab — it directly trains the "what happens when the variable changes" reasoning that appears in ALE scenario questions. Every control must be designed for clarity and precision.

Slider component specificationExact dimensions, states, value display
Track: Height 4px. Background #E0DED8 (border color). Border-radius 2px. Full width of panel minus 16px padding each side.
Fill: Height 4px. Background #1B3FC4 (Cobalt Blue). Border-radius 2px. Transition: none on drag (must feel immediate), 150ms ease on programmatic changes.
Thumb: 14×14px circle. White fill. 2px Cobalt Blue border. No box-shadow. On hover: border-width 2.5px. On drag: scale 1.2. Minimum touch target 44px (use padding-based invisible expansion).
Value display: Right-aligned DM Mono 12px 500wt Cobalt Blue. Shows current value with unit (mm). Updates live as slider moves. Must use Math.round() — never display decimal millimeters.
Range labels: Min and max values displayed below track in DM Mono 9px ink-muted. Format: "min 250" / "max 200". The code limit is labeled explicitly so the student knows exactly where compliance ends.
Limit state: When slider is at maximum allowed value, the track fill turns Signal Gold. This is the "at limit" warning — the student can see they're at the code maximum without reading a number.
Violation state: When a slider would exceed the code maximum (for modules that allow exceeding limits to demonstrate violations), the fill turns Signal Red. The thumb gains a red ring. The compliance indicator at the bottom updates immediately.
Step value: Always step="1" for millimeter values. For ratio values (slope = 1:N), use step="0.5".
// Slider component — Tailwind classes and state logic
function ParametricSlider({ label, value, min, max, unit, codeMax, onChange }) {
  const pct = ((value - min) / (max - min)) * 100
  const isAtLimit   = value === codeMax
  const isViolation = value > codeMax

  const fillColor = isViolation ? 'bg-signal-red'
                 : isAtLimit   ? 'bg-signal-gold'
                 :               'bg-primary'

  return (
    <div className="flex flex-col gap-1.5">
      <div className="flex justify-between items-baseline">
        <label className="text-[11px] text-ink-2">{label}</label>
        <span className="font-mono text-[12px] font-medium text-primary">
          {Math.round(value).toLocaleString()} {unit}
        </span>
      </div>
      <div className="relative h-4 flex items-center">
        <div className="w-full h-1 bg-border rounded-full">
          <div className={`h-full rounded-full transition-colors ${fillColor}`}
               style={{ width: `${pct}%` }} />
        </div>
        <input type="range" min={min} max={max} step="1" value={value}
               onChange={e => onChange(Number(e.target.value))}
               className="absolute inset-0 opacity-0 cursor-pointer w-full" />
      </div>
      <div className="flex justify-between">
        <span className="font-mono text-[9px] text-ink-muted">min {min}</span>
        <span className="font-mono text-[9px] text-ink-muted">max {codeMax}</span>
      </div>
    </div>
  )
}

Chapter 07 Onboarding — Per-Module First-Time Experience
Every student who opens a 3D module for the first time needs to understand three things in under 20 seconds: what they're looking at, how to move around, and what to do first. The onboarding must never interrupt the learning session — it is a brief orientation, not a tutorial.

Shown once, the first time any student opens any 3D module. Never repeated unless the student explicitly requests it. Teaches: orbit, zoom, hotspot click. 3 cards, swipeable, dismissible.

Auto-dismiss timer: 6 seconds. A thin cobalt progress bar runs along the bottom of the card. The student can see the timer running, which creates gentle urgency to read without forcing it.
Interaction dismiss: Any tap, drag, or scroll on the canvas immediately dismisses the card. It does not interrupt — it yields to the student's intent.

Chapter 08 Loading, Empty & Error States
All required states — specification
P1
Loading state: The canvas background (cream) renders immediately. A centered cobalt spinner (not a full-page spinner — a small 24px circular indicator) appears while the GLB loads. Below it: module name in DM Mono 10px. Progress percentage if available from the GLB loader. Never a blank white screen.
Empty state (module list): When no 3D modules are available for a topic: "No 3D model yet for this topic. Check back — we're building it." DM Mono eyebrow, 2-line Inter body. Never "Coming soon" — always honest about the current state.
Error state (GLB fails to load): The canvas area shows: a simple architectural line drawing (SVG placeholder) of the topic + "3D model unavailable. The wiki article has all the information you need." Link to the relevant wiki section. Never a red error message — calm, informative, redirects.
Low performance warning: If FPS drops below 20 for more than 3 seconds, show a dismissible toast at the bottom: "This model is running slowly. Try closing other tabs for a better experience." Signal Gold background. Dismissed with one tap. Never blocks interaction.
Mobile fallback: On screens narrower than 375px (very small phones), the full 3D module may not render well. Show a static annotated screenshot of the model with a message: "3D Lab works best on larger screens. The annotated diagram below has all the same information." This is a last-resort fallback — the 3D Lab targets 375px+ screens.

Chapter 10 Implementation Sequence
Build in this exact order. Each phase must be fully tested before the next begins. A broken hotspot interaction in Phase 1 invalidates everything built on top of it in Phase 2.
Phase 1 · 1
TypeScript interfaces + Zustand store
Define all types in src/types/3d-lab.ts and the Zustand store shape in useLabStore.ts. Nothing else starts until these are written and reviewed. Interfaces are the contract for everything that follows.
Phase 1 · 2
LabCanvas.tsx — scene setup only
Canvas with cream background, lighting, OrbitControls, ContactShadows. No model yet. Test that the scene renders, camera orbits correctly, and performance baseline is acceptable. Target: 60fps on a mid-range laptop with an empty scene.
Phase 1 · 3
GLB model loading + LabViewer wrapper
Load the first GLB (Accessible Toilet). Verify shadows, materials, performance (under 5MB GLB at 60fps). Build LabViewer with the dark top bar and basic layout. Test loading state and error state with a broken URL.
Phase 1 · 4
HotspotDot.tsx — all states
Build the dot with idle, hover, active, and visited states. Test all three types (cobalt, gold, red). Verify distanceFactor keeps dots visually consistent at all zoom levels. Verify pulse animation is smooth at 60fps.
Phase 1 · 5
InfoPanel.tsx — full implementation
Build the info panel with all states: default, gold variant, positioning logic, values table, source line, CTA. Test left/right positioning logic on both halves of the viewport. Test mobile bottom-sheet fallback.
Phase 1 · 6
QuestionPanel.tsx + answer flow
Build the question panel: stem, 4 options, selection lock, correct/wrong states, rationale display, back-to-model link. Connect to Zustand store. Test correct and wrong answer paths. Verify heatmap update fires silently.
Phase 2 · 7
ToolPalette.tsx — all buttons
Build the dark floating toolbar with all 6 buttons and their states. Wire reset camera to the Zustand store. Wire label toggle. Cross-section and exploded view buttons exist but are disabled until Phase 3.
Phase 2 · 8
OnboardingFlow.tsx + ModuleContextCard.tsx
Build both tiers of onboarding. Implement localStorage gating. Test: new user sees full onboarding, returning user skips it. Test auto-dismiss timer on the module context card.
Phase 2 · 9
ParameterPanel + ParametricSlider
Build the parametric control panel and slider component with all three fill states (cobalt, gold, red). Wire to a parametric module (Stairway Configurator). Test live model updates as slider moves. Test compliance indicator updates.
Phase 3 · 10
Cross-section + Exploded view
Implement the cut plane for cross-section mode. Implement component separation animation for exploded view. These require per-module configuration — only implement for modules where the interaction is meaningful.
Chapter 11 Non-Negotiable Rules
✕ Never auto-rotate the camera on load
✕ Never auto-advance through hotspots
✕ Never show more than 5 hotspot dots simultaneously
✕ Never use AI-generated 3D models — precision required
✕ Never add gamification to the 3D Lab
✕ Never block the model with a splash screen
✕ Never place a hotspot that doesn't have an attached question
✕ Never use a color outside the design token set
✕ Never exceed 5MB GLB file size
✕ Never put more than 2 sentences in a hotspot label
✓ Always provide error + loading + empty states
✓ Always test on 375px mobile viewport
✓ Always dispose R3F geometry on unmount
✓ Always use distanceFactor on Html hotspots
The governing question for every 3D Lab decision: Does this spatial interaction help a student understand a building code provision or architectural concept better than reading about it in text? If yes, build it. If no, don't build it. The 3D Lab earns its place in the product by solving a learning problem that 2D cannot solve. Every feature that doesn't serve that purpose is extraneous cognitive load.
