**Branch:** `feat/landing-3d-hero-best-representation`

## 1. Strategic correction from Philip

Philip clarified that the best language is not simply “study tool” or even only “study companion.” The stronger territory is:

> **SlateCamp as an architecture knowledge resource and atlas.**

This matters because “study tool” sounds like:

- a quiz app;
- a dashboard;
- a method product;
- a temporary exam crutch;
- a generic feature checklist competing for attention.

“Atlas” sounds like:

- map;
- orientation;
- organized territory;
- a resource you keep returning to;
- architecture-native drawing/document language;
- school-to-board-to-practice continuity;
- SlateCAMP as a place you navigate, not just software you operate.

The strategic north star should become:

> **SlateCamp is an architecture knowledge atlas: source-backed resources, visual explanations, quizzes, 3D labs, and practical tools that help students and reviewees navigate architecture knowledge with confidence.**

## 3. Why “Atlas” fits SlateCamp better than “Study Tool”

### A. Brand fit

`SlateCamp` already implies travel, navigation, terrain, trails, maps, checkpoints, and preparation. “Atlas” extends the metaphor naturally:

- Camp = where you prepare.
- Trail = the path through topics.
- Atlas = the map of the territory.
- Field guide = what you consult in the field.
- Readiness map = what shows where you stand.

### B. Architecture fit

Architecture is inherently spatial and document-based:

- plans;
- sections;
- grids;
- sheets;
- codes;
- annotations;
- title blocks;
- references;
- diagrams;
- maps;
- site analysis.

An atlas lets SlateCamp feel architecture-native instead of edtech-native.

### C. Market fit

The target market is not primarily buying a quizzing method. They are trying to solve:

- “Where do I find the reliable rule?”
- “What does this code provision mean?”
- “How do I connect this topic to exam questions?”
- “What am I missing?”
- “What should I repair before it is too late?”

An atlas answers those needs better than a “study tool.”

## 7. Three.js hero direction: “SlateCamp Atlas Field”

### Concept

A transparent WebGL scene where architecture knowledge appears as a living atlas:

1. scattered study fragments, sheet plates, nodes, and guide lines appear loosely arranged;
2. they organize into subject zones and resource paths;
3. a calm route appears from `Look up` → `Understand` → `Test` → `Repair`.

### Geometry primitives

Use simple, performant primitives:

- instanced points/nodes;
- thin line segments and curves;
- translucent sheet planes with non-readable markings;
- soft grid floor or background grid;
- small floating markers;
- optional folded ribbon/aurora line made from shader material.

### Architecture cues

- title block rectangles;
- grid bubbles;
- sheet indexes;
- dashed guide lines;
- contour-like paths;
- section/elevation markers;
- redline annotations used sparingly;
- code/page locator tags in DOM.

### Motion

- one-time organization animation on load;
- subtle cursor parallax;
- ambient drift after settling;
- no orbit controls;
- no public knobs/toggles;
- reduced-motion fallback: static organized atlas image/DOM card.

### Emotional story

> Scattered material becomes a map. The map gives comfort. The comfort leads to action.

## 8. JavaScript/package evaluation

### Already installed and sufficient for first implementation

From `package.json`:

- `three` `^0.183.2`
- `@react-three/fiber` `^9.6.1`
- `@react-three/drei` `^10.7.7`
- `@use-gesture/react` `^10.3.1`
- `framer-motion` `^12.38.0`

These are enough to build an excellent hero without new dependencies.

### Current npm package checks performed

Checked via `npm view` on 2026-05-07:

- `maath` latest `0.10.8`, MIT
- `@react-three/postprocessing` latest `3.0.4`, MIT
- `postprocessing` latest `6.39.1`, Zlib
- `troika-three-text` latest `0.52.4`, MIT
- `three-mesh-bvh` latest `0.9.9`, MIT
- `leva` latest `0.10.1`, MIT
- `gsap` latest `3.15.0`, Standard no-charge license
- `@theatre/core` latest `0.7.2`, Apache-2.0
- `@splinetool/react-spline` latest `4.1.0`

### Recommended package posture

#### Use approved hero motion helper: `maath`

Potential use:

- damped easing;
- better smooth motion inside R3F;
- curve/math helpers;
- elegant, stable animation values.

Recommendation:

> **Approved yes** for the hero implementation when building the Atlas Field motion system. Use it intentionally for smooth damped movement rather than adding a larger animation framework.

#### Avoid first-pass: `@react-three/postprocessing`

Potential use:

- bloom;
- depth of field;
- subtle glow;
- vignette.

Risk:

- heavier above-the-fold;
- easier to make the hero look like sci-fi/game UI;
- more complexity for reduced-motion/performance.

Recommendation:

> **Not first-pass.** Consider only after the base hero is already beautiful and performant. Use CSS/Three materials first.

#### Avoid: `troika-three-text` unless labels must be in-canvas

The hero should keep critical labels in DOM for accessibility and SEO. Canvas text is visually useful but should not carry core copy.

Recommendation:

> **Avoid first-pass.** Use DOM labels positioned around the canvas.

#### Avoid: `leva`

Great for developer controls, wrong for public hero controls.

Recommendation:

> **Do not ship in landing hero.** If used, it should be dev-only and not bundled into public UI.

#### Avoid: `GSAP`

GSAP is powerful but unnecessary for this hero. Existing Framer Motion + R3F can handle the needed entrance, parallax, and organization motion. Also avoid adding license ambiguity until there is a clear need.

Recommendation:

> **Do not add now.** Reconsider only for a complex scroll narrative below the fold.

#### Avoid: Theatre.js

Useful for timeline-heavy art direction, but overkill for the current need and adds authoring complexity.

Recommendation:

> **Do not add for MVP hero.**

#### Avoid: Spline runtime

Spline may speed up 3D composition but reduces code-level control, can add runtime weight, and may make the hero less integrated with SlateCamp’s existing R3F stack.

Recommendation:

> **Do not add.** Build natively in R3F.

#### Avoid: Remotion for live hero

Remotion is useful for rendered videos, ads, trailers, or static marketing assets. It is not the right tool for a live interactive transparent WebGL hero.

Recommendation:

> **No for the landing hero. Yes later for ads/social/video assets if needed.**

### Package conclusion

The greatest landing page is not achieved by adding many packages. It is achieved by:

1. a stronger category: architecture knowledge atlas;
2. a clear first-scroll hierarchy;
3. one iconic 3D visual system;
4. motion that organizes knowledge rather than showing off;
5. reliable, plain-language copy;
6. performance discipline.

First implementation should use existing packages plus `maath` for smooth Atlas Field motion where it improves the feel. Keep the dependency story intentional: `maath` is approved because its damped interpolation utilities fit premium R3F motion without bringing in a heavy animation framework.

## 11. Decision recommendation

Adopt this hierarchy:

1. **Homepage hero:** Atlas / resource positioning.
2. **Board-review section:** fear-to-clarity/readiness pathway.
3. **Personal field-guide section:** user transformation/Pokedex-style positioning.
4. **Visual system:** one SlateCamp Atlas Field: floating sheet stack + review constellation + dotted blueprint field.
5. **Package strategy:** use existing R3F/Drei/Three/Framer stack with `maath` approved for Atlas Field motion; do not add GSAP, Remotion, Spline, Theatre.js, or postprocessing in the first pass.

This gives SlateCamp a more durable identity than “study tool” and a more ownable landing-page world than a literal setback widget.
