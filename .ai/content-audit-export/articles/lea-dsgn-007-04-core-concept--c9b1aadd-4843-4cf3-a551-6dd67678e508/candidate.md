# Architectural design process

## What You Need to Know for the LEA

## Learning Goal
Use the architectural design process as an evidence-managed sequence: identify the problem, gather and analyze information, synthesize proposals, evaluate against goals, iterate with feedback, and translate decisions into coordinated documents.

The checked design-process source defines architectural design as generating proposals that transform an existing condition into a better future condition. It lists initiation as problem identification, preparation as collection and analysis of information, proposal-making as synthesis, evaluation as testing against goals, and iteration as cycles with feedback.

Architectural programming is the problem-seeking phase. It gathers, organizes, analyzes, interprets, and presents information relevant to the project. A responsible program distinguishes existing-state facts from future-state goals: the setting, physical site data, client/user profile, constraints, mission, goals, performance requirements, and concepts.

An issue-based program separates issues, facts, values, goals, performance requirements, and concepts. Facts are objective and verifiable by measurement or observation. Values explain why different users and building types may require different responses to the same issue. Goals state design intention. Performance requirements describe measurable function. Concepts organize relationships among form, material, color, adjacency, and other elements under the architect's control.

Mechanical and electrical design references add a practical warning: design decisions made early can affect operating costs, maintenance, comfort, enjoyment, and productivity for years. Predesign defines the project brief or owner requirements; later design phases develop drawings and specifications that allow construction.

| Process step | Source-safe purpose |
| --- | --- |
| Initiation | Identify the problem or issue that demands design. |
| Preparation | Collect and analyze site, user, legal, technical, market, and physical information. |
| Proposal-making | Synthesize a design response from multiple constraints and values. |
| Evaluation | Test the proposal against goals and performance requirements. |
| Iteration | Revise through cycles and feedback before locking downstream documents. |

Do not treat design development, construction documents, or construction administration as isolated drafting labels. The LEA-safe answer is to ask what information is available, what decision is being made, which consultant input is required, and whether the decision has been validated before the next stage.

## Key Takeaways

Programming is problem-seeking; schematic and later design work should respond to the program rather than replace it.

Facts, values, goals, performance requirements, and concepts are different kinds of design information.

Iteration is part of the process; late discoveries usually signal that required information or coordination was skipped earlier.
