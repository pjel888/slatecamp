## Required Freshness Metadata for Phase 1B

Phase 1B **must not** use stale or unproven exports. The following metadata must be present in any export manifest used for editorial decisions:

### Mandatory Fields

| Field | Purpose | How to Obtain |
|---|---|---|
| `exported_at` | Timestamp of export completion | Generated by export script |
| `project_ref` | Supabase project identifier | `inferSupabaseProjectRef()` or env var |
| `migration_version` | Latest applied migration at export time | Query `supabase_migrations.schema_migrations` or local migration list |
| `article_count` | Total articles exported | Count from DB or local dirs |
| `question_count` | Total questions exported | Count from DB or local dirs |
| `source_count` | Total sources exported | Count from DB or local dirs |
| `hash_algorithm` | Algorithm used for content hashing | Script constant (`sha256`) |
| `aggregate_content_hash` | Hash of all per-article content hashes | Computed by script |
| `script_version` | Version or git commit of export script | `package.json` version or `git rev-parse HEAD` |
| `script_path` | Which script produced the export | `scripts/content-audit/export-article-bundles.ts` |

### Recommended Fields

| Field | Purpose | How to Obtain |
|---|---|---|
| `git_commit` | Repository commit at export time | `git rev-parse HEAD` |
| `git_dirty` | Whether working tree had uncommitted changes | `git status --porcelain` |
| `normalized_at` | Timestamp of normalization completion | From `normalize-article-bundles.ts` run log |
| `normalized_by_script` | Script that performed normalization | `scripts/content-audit/normalize-article-bundles.ts` |
| `live_db_checksum` | A lightweight DB-level checksum or max(updated_at) | `SELECT max(updated_at) FROM wiki_articles` |

### Freshness Validation Checklist

Before any Phase 1B script reads local exports, it must verify:

1. [ ] `exported_at` is within acceptable staleness window (Phase 1A evidence: documented; Phase 1B active editorial session: recommend ≤ 6 hours).
2. [ ] `article_count`, `question_count`, `source_count` match live Supabase counts.
3. [ ] `migration_version` exactly matches live applied migration endpoint unless a documented local-only plan explains the delta. Migration equality is a hard Phase 1B gate.
4. [ ] `git_commit` matches current HEAD (or is documented as intentionally different).
5. [ ] Per-article `content_hash` in manifest matches recomputed hash of local `original.md`.
6. [ ] `normalized_at` exists and is ≥ `exported_at` (proves normalization ran after export).
7. [ ] Every article bundle has required files (`original.md`, `article-metadata.json`, `linked-questions.json`, `sources.json`) and every file hash matches the manifest.
8. [ ] Every linked question in per-article bundles is accounted for in the exported question count or explicitly excluded with reason.

## Staleness Scenarios That Block Phase 1B

| Scenario | Risk | Mitigation |
|---|---|---|
| Export > 6 hours old for Phase 1B | Live DB may have changed; local edits could conflict | Re-export before Phase 1B start |
| Count mismatch (local ≠ live) | Export incomplete or DB mutated after export | Re-export or investigate discrepancy |
| Migration version mismatch | Local schema assumptions may not match live | Verify live applied migrations |
| Missing normalization timestamp | Cannot trust ui-block or parser data | Re-run normalization |
| Uncommitted working-tree changes | `git_dirty = true` means script behavior may differ from committed code | Commit or stash changes before export |

## What Remains Safe for Phase 1A

- Using the current export for read-only inventory, contradiction mapping, and candidate selection.
- Using count-matching as a coarse freshness signal.
- Manual verification that `ui-blocks.json` timestamps post-date `export-summary.json`.

## What Blocks Phase 1B

- **No automated freshness gate.** Phase 1B scripts need a deterministic `isExportFresh()` function that enforces the checklist above.
- **No git/script version provenance.** If a bug is found in an export artifact, there is no way to know which code version produced it.
- **No migration-version anchor.** A schema change (e.g., new `wiki_articles` columns) between export and implementation could invalidate assumptions.
- **No aggregate hash.** Verifying 567 individual files is possible but slow; an aggregate hash would enable fast integrity checks.

## What Claude Should Review Next

2. Whether a standalone `scripts/content-audit/verify-export-freshness.ts` should be created as a Phase 1B prerequisite.
3. Whether the staleness window (24 hours) is appropriate, or whether it should be shorter for high-risk editorial work.
4. Whether `export-summary.json` should include an `aggregate_content_hash` field for fast integrity verification.
