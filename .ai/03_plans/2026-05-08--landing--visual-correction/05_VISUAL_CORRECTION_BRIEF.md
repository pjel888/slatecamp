# 05 — Visual Correction Brief: SlateCamp Landing Page

Date: 2026-05-08
Status: design brief only, no implementation

## One-line brief

Transform the landing page from a card-based edtech/product-tour page into a premium interactive architecture knowledge atlas: calm, spatial, source-aware, and emotionally useful to students who feel lost in scattered review material.

## Hard constraint

No hero with a 3D object inside a rounded card.

This is the central design correction.

## What must remain from the current attempt

Potentially keep or reinterpret:

- dotted grid background
- atmospheric background image/texture language
- architecture knowledge atlas positioning
- source-backed/resource platform copy direction
- assurance/comfort/reliability as emotional target

Everything else is open for redesign.

## Emotional target

The landing should make the user feel:

- oriented
- calmer
- held by a reliable system
- curious to explore
- less lost in scattered notes/codes/reviewers
- supported, not sold to

It should not make the user feel:

- like they are looking at another SaaS dashboard
- like they are being shown fake product cards
- like the site is chasing Dribbble trends
- like architecture has been reduced to blueprint gimmicks
- like SlateCamp is pretending to be a review center

## Visual target

SlateCamp should feel like:

- an authored digital atlas
- an architecture field guide
- a spatial archive
- a quiet interactive publication
- a map you can enter
- a reference system with depth and atmosphere

It should not feel like:

- generic edtech SaaS
- a quiz app splash page
- a Notion/Linear clone with 3D decoration
- a dashboard screenshot collage
- a startup bento grid
- a glassmorphism card stack

## Hero requirements

### Required

- Visual field integrated into the full hero/viewport.
- No main 3D card or right-side framed module.
- The 3D/canvas/background should carry the atmosphere of the page.
- Copy must be sparse and human.
- CTA must be simple and truthful.
- The dotted/background language may provide continuity.
- Visual must evoke architecture through spatial behavior, not literal labels.

### Prohibited

- primary hero visual inside `rounded-*` card/panel
- floating UI pills as the main device
- fake dashboard/product screenshot as first impression
- a labelled 3D module like "Setbacks / Codes / Egress" floating in a box
- multiple metric cards in hero
- "world-class" public claim
- SRS/active recall/quizzing mechanics in hero

## Good hero behavior, described without cheesy concept names

The hero can be abstract if it behaves correctly.

Acceptable behaviors:

- scattered points/marks gradually resolving into a navigable field
- a quiet spatial grid with depth, parallax, and atmospheric light
- architecture-like layers that imply plan/section/elevation without literal blueprint gimmicks
- source/knowledge nodes that feel like coordinates in an atlas, not UI badges
- a field that responds subtly to pointer/scroll
- one strong visual rhythm that continues into the next section

Unacceptable behaviors:

- floating glass cards
- literal house model in a box
- dashboard screenshot
- cute labels orbiting an object
- overly symbolic named metaphors
- neon tech demo detached from architecture learning

## Page rhythm requirements

The page should not go:

1. hero card
2. quiz card
3. wiki card
4. 3D card
5. analytics card

Better rhythm:

1. **Entry field**
   - calm atlas/world hero
   - category and promise

2. **The student's problem**
   - scattered review materials
   - mock-board anxiety
   - code/table overwhelm
   - need for next useful step

3. **Atlas model**
   - how SlateCamp organizes knowledge
   - topic map / wiki / source notes / visual explanations / practice / analytics
   - expressed as a system, not a card pile

4. **Real product paths**
   - Wiki: find and understand
   - Practice: check what stayed
   - 3D Lab: see spatial rules where available
   - Analytics: identify weak topics and study activity
   - Use actual product primitives and accurate access boundaries

5. **Trust and boundaries**
   - supplementary resource
   - not a review center
   - not official
   - no guarantees
   - verify current requirements

6. **CTA**
   - start with free/account path truthfully

## Section design correction

### Problem section

Should feel editorial/human, not like a feature grid.

Possible structure:

- large text statement
- sparse bullets in student language
- background grid/field continuity
- one atmospheric image/mark

Avoid:

- three generic feature cards
- icons with marketing blurbs

### Product map section

Should be a map/layer system, not a bento grid.

May use:

- four product paths as atlas coordinates
- numbered sections
- lines/paths/layers
- small source/update metadata
- restrained cards only if content-native

The four paths:

- Wiki / resources — find the concept
- Practice — check what stayed
- 3D Lab / visuals — see spatial rules where available
- Analytics / dashboard — know what to revisit

### Quiz section

Must reference real quiz behavior.

Use language like:

- "Practice checks what stayed."
- "When mappings are available, missed topics can point back to explanations and related articles."
- "Different modes support quick checks, focused review, simulations, and endurance."

Avoid:

- fake quiz card as a pretend product screenshot
- "every missed answer becomes..." absolute claim
- gamified/edtech energy

### 3D Lab section

Must not be a fake SVG in a card.

Options:

- treat 3D as part of the atmospheric visual system, not a section mockup
- show actual available module categories later with access caveat
- use stills/screenshots from real modules only if accurate
- make entitlement/access copy truthful

Required copy caveat:

- Available lab access depends on account/plan/entitlement.
- Educational visual companion; verify current requirements with primary authorities.

### Wiki/resources section

Should lean into the Pokedex/field-guide metaphor without becoming childish.

Use:

- search/browse/find behavior
- related topics
- source notes
- updated notes
- practice from article context

Avoid:

- pretending every topic has perfect source coverage
- official-source implication

### Trust section

Should be explicit and calm.

Required ideas:

- supplementary resource
- no pass guarantee
- not affiliated with PRC/PRBoA/universities/government agencies
- not a primary review center
- use alongside school, review center, primary documents, and professional guidance

## Visual acceptance criteria

Before implementation, a static mock/design direction must score:

- Hero is not carded: pass/fail
- Feels like architecture knowledge atlas, not SaaS: ≥9/10
- Visual restraint / non-cheesy: ≥9/10
- Reference-site alignment: ≥8.5/10
- Product truth: ≥9/10
- User emotional clarity: ≥9/10
- Legal/trust safety: ≥9/10
- Mobile feasibility: ≥8/10
- Performance feasibility: ≥8/10

If the hero has a right-side carded 3D module, it fails automatically.

## Pre-implementation process required

1. Gather reference screenshots/notes.
2. Produce 2–3 static visual directions as docs or mockups, not code.
3. Compare each against this brief.
4. Reject any direction that looks like generic SaaS/edtech.
5. Get Philip's approval on one direction.
6. Only then implement.

## Final design principle

SlateCamp should not announce that it is premium.

It should feel premium because:

- the page has taste
- the visual system is authored
- the copy understands the student
- the product claims are truthful
- the structure is calm and precise
- the architecture emotion is spatial, not decorative
