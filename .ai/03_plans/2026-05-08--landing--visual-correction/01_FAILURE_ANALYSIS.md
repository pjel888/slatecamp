# 01 — Failure Analysis: Why the Current Landing Direction Failed

Date: 2026-05-08
Status: supersedes the previous card-based hero direction

## Short verdict

The current landing redesign is technically functional but visually wrong.

It failed because it converted a premium Three.js / architecture-atlas ambition into a familiar SaaS/edtech layout: text on the left, a framed 3D module/card on the right, then more feature preview cards below.

That is not what the reference sites do. It is also not what Philip asked for.

## Primary failure

### The hero became a product card, not a world

The current hero presents the Three.js visual as a contained object inside a rounded panel/card. It has UI-like badges and labels around the object.

This creates the wrong emotion:

- safe but generic
- dashboard-like
- edtech/SaaS
- predictable
- decorative rather than authored
- a module preview instead of a destination

The reference standard is different. The best Three.js sites treat the visual as:

- the atmosphere
- the world
- the stage
- the navigation metaphor
- the identity system
- the thing the user enters

The text may overlay it, orbit it, interrupt it, or sit in tension with it, but the scene is not trapped inside a card.

## Secondary failure

### The rest of the page inherited the same generic section logic

The problem is not only the hero.

Current marketing sections include hard-coded previews like:

- quiz preview card
- 3D Lab SVG mockup card
- analytics/readiness mockup-style cards
- wiki/resource preview cards

These look like product screenshots, but they are mostly illustrative/static approximations. Worse, they repeat the same container/card logic that already failed in the hero.

This turns the landing into:

1. hero card
2. quiz card
3. 3D card
4. analytics card
5. CTA card

That rhythm does not feel like a high-end architecture knowledge atlas. It feels like a startup template.

## Taste mismatch

The previous suggestions used predictable concept names like "Blueprint Aurora," "Floating Sheet Storm," "Section-Cut Sculpture," etc. Those are too literal and cheesy.

The correction should not begin by inventing cute concept names. It should begin by defining:

- spatial behavior
- emotional target
- art-direction constraints
- reference-site mechanics
- product truth
- typography system
- section pacing

If a concept sounds like a Dribbble prompt, reject it.

## What Philip already identified as usable

Philip explicitly said the only parts that are working now are:

- dotted grid background
- background image / atmospheric background direction

Preserve those as possible visual DNA.

Do not preserve:

- carded 3D module
- UI labels around the hero object
- fake designer-showcase modules
- generic SaaS feature cards
- literal quiz/product previews that do not match the dashboard

## What was misunderstood

### Misunderstanding 1: Technical QA ≠ design approval

The previous pass overvalued:

- type-checks
- build success
- visual scoring by an automated reviewer
- WebGL fallback reliability

Those matter only after the direction is right. They cannot redeem a bad art direction.

### Misunderstanding 2: Architecture does not mean literal blueprint gimmicks

The design can evoke architecture without using predictable motifs everywhere:

- blueprint labels
- floating sheets
- neon grid cards
- isometric house diagrams
- fake plan-view mockups
- technical UI chips

Architecture emotion can come from:

- scale
- void/solid tension
- measured spacing
- sectionality
- procession
- material restraint
- light/dark contrast
- weight
- atmosphere
- silence
- precision
- spatial hierarchy

### Misunderstanding 3: Product proof does not require fake product cards

The landing should reference the real dashboard and app behavior. It should not fabricate glossy preview cards that imply exact app surfaces.

For example:

- The real dashboard has readiness ring, heatmap, weekly stats, and analytics.
- The real quiz system has modes, sessions, explanations, confidence, wiki links, and results.
- The real 3D Lab is gated and currently has a limited visible module set.
- The real wiki has article pages, source sidebars, headings, related topics, read tracking, and practice links.

The landing should express these truths without creating fake screenshots that overpromise.

## Current landing anti-patterns to reject

Reject any future direction if it contains:

- a primary hero visual inside a rounded card
- "3D module on the right" composition
- floating pills/badges around the hero scene
- dashboard mockup as the main first impression
- generic app screenshot collage
- glassmorphism panels as the design idea
- feature bento as the main storytelling system
- fake statistics like `42% → 98%`
- "every missed answer becomes..." absolute claims
- free/full 3D Lab claims that ignore entitlement gating
- SRS/active recall/quizzing method copy in the hero
- public "world-class" bragging

## Directional correction

The landing should feel less like:

- edtech SaaS
- quiz app
- dashboard product tour
- generic AI study tool
- review center alternative

And more like:

- architecture knowledge atlas
- field guide
- calm reference system
- spatial archive
- companion for finding concepts quickly
- source-aware resource beside school/review/apprenticeship
- premium interactive publication

## Design quality principle

A premium landing page does not need to explain every feature in the hero.

It should first establish:

- category
- feeling
- trust posture
- visual identity
- reason to continue

Then sections can reveal product surfaces with increasing specificity.
