# Stairway Workbench Prototype Correction Brief

Date: 2026-05-13
Status: correction after Philip review

## What failed

The first prototype set misunderstood the goal.

Problems:
- It made Philip choose between separate “modes” instead of presenting one excellent default learner experience.
- It over-centered violation/diagnosis states.
- It made the module feel like an error dashboard instead of a beautiful stairway learning configurator.
- It treated failure states as the main prototype state, when the default experience should be a calm, passing, premium learning scene.
- The variants were too schematic and not visually good enough.

## Corrected direction

Create one strong default prototype first.

The default must:
- open in a passing/compliant state;
- feel premium, spacious, and architectural;
- keep the 3D stair as the dominant object;
- show live compliance as a supportive right-side learning layer, not an alarm wall;
- use controls as a clean parameter studio, not a cramped sidebar dump;
- include violation behavior only as a secondary state after the passing baseline is established;
- avoid forcing the user to choose between “modes” during visual direction selection.

## New prototype target

Name:
`variant-d-premium-passing-workbench.html`

Purpose:
A single best-shot prototype for the target default experience.

Default state:
- Passing/compliant stair.
- Scenario selected.
- Core dimensions cleanly visible.
- Right panel says “Passing under active checks.”
- Violations hidden unless the learner intentionally drags a dimension past a threshold.
- Source audit pending shown quietly, not as a major warning.

Interaction:
- One simulated slider/toggle can switch to a violation state.
- The visual design should prove that passing/default state is beautiful before showing failure.

Non-goal:
Do not make Philip choose among modes at this stage.
