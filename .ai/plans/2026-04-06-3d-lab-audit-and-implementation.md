# 3D Lab Comprehensive Audit
## 1. Technical & Network Audit
- The current 3D Lab route mixes two incompatible layout contracts. [`src/app/dashboard/3d-lab/page.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/app/dashboard/3d-lab/page.tsx) renders either a browser or a viewer inside the inherited dashboard shell, but it still documents the viewer as a standalone surface with "no sidebar". At the same time, [`src/app/dashboard/3d-lab/layout.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/app/dashboard/3d-lab/layout.tsx) mounts a viewport-wide fixed R3F canvas for the entire subtree, which means the index page, query-param viewer, and nested subroutes all inherit full-screen rendering behavior whether they need it or not.
- Navigation is not canonical. The dashboard allowlist in [`src/features/3d-lab/config/dashboard-visibility.ts`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/3d-lab/config/dashboard-visibility.ts) exposes `site-development-controls`, `stairway-configurator`, `calculator-flooring`, and `unified-wall-configurator`, while [`src/components/sidebar/sidebar-constants.ts`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/components/sidebar/sidebar-constants.ts) links to `?model=nbcp-envelope` and `/dashboard/3d-lab/wall-configurator`. The feature therefore has multiple competing URLs and multiple shells for "module detail".
- The feature extraction is only partial. [`src/features/3d-lab/components/LabViewport.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/3d-lab/components/LabViewport.tsx) still imports route-private `_templates`, `_scenes`, and module config files from `src/app/dashboard/3d-lab/_*`, so the feature package cannot own its rendering runtime, testing surface, or state boundaries cleanly.
- The browser page pays a WebGL tax before the user opens a module. Because the persistent canvas lives in the route layout instead of a viewer-only shell, the index experience mounts the full graphics stack even when it only needs a grid of cards.
- The network path is incomplete. [`src/lib/lab-analytics.ts`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/lib/lab-analytics.ts) queues events for `/api/analytics/3d-lab`, but no matching API route exists in `src/app/api`. The result is a telemetry contract that is defined in code but not backed by a real endpoint.
- The live module experience is not wired to its own session pipeline. [`src/lib/actions/lab.ts`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/lib/actions/lab.ts) defines `create3DLabSession`, `record3DLabInteraction`, and `get3DModuleBySlug`, but the current viewer route does not call them, so persistence, mastery updates, and hotspot-backed content are disconnected from the visible product.

## 2. UI, UX & Component Architecture Audit
- The feature has a shared browser, but it does not have a shared module shell. The four visible modules route into materially different runtimes: `site-development-controls` uses a bespoke dashboard, `stairway-configurator` uses the parametric template, `calculator-flooring` uses the calculator template, and `unified-wall-configurator` exists both as a query-param template and as a separate `/wall-configurator` page. That is the core reason the module pages feel structurally unrelated.
- Typography and surface styling are inconsistent across the shell components. [`src/features/3d-lab/components/LabBrowser.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/3d-lab/components/LabBrowser.tsx), [`src/features/3d-lab/components/CategoryGrid.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/3d-lab/components/CategoryGrid.tsx), [`src/features/3d-lab/components/ModuleList.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/3d-lab/components/ModuleList.tsx), [`src/features/3d-lab/components/LabTopBar.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/3d-lab/components/LabTopBar.tsx), [`src/features/3d-lab/components/ModuleContextCard.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/3d-lab/components/ModuleContextCard.tsx), [`src/features/3d-lab/components/InfoPanel.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/3d-lab/components/InfoPanel.tsx), and [`src/features/3d-lab/components/OnboardingFlow.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/3d-lab/components/OnboardingFlow.tsx) all mix hardcoded hex colors, inline `fontFamily`, fixed pixel sizes, and ad hoc spacing instead of shared design tokens and component primitives.
- The module metadata shell is synthetic rather than data-backed. [`src/features/3d-lab/components/ModuleViewer.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/3d-lab/components/ModuleViewer.tsx) builds a shim `ModuleConfig` with empty hotspots, a fixed `estimatedMinutes: 5`, `visitedCount={0}`, and `hotspots={[]}`. This means the top bar, context card, and onboarding layer are not describing the real module state.
- Overlay ownership is fragmented. `LabTopBar`, `ModuleContextCard`, `OnboardingFlow`, `InfoPanel`, and the template-specific panels all manage their own `fixed` or `absolute` positioning, z-index, shadow, and spacing rules. Without a single overlay layout system, every module template creates its own collision and stacking behavior.
- The wall configurator is visually isolated from the rest of the feature. [`src/features/wall-configurator/components/WallConfigurator.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/wall-configurator/components/WallConfigurator.tsx) renders a standalone `min-h-screen` wizard with its own header and summary bar, so it does not inherit any 3D Lab module framing, browser-to-viewer continuity, or shared information hierarchy.
- Containerization debt remains in both directions: promoted feature components exist, but route-private `_components`, `_templates`, `_scenes`, `_stores`, and legacy library copies still coexist. The result is a feature that looks partially modularized in the browser layer and largely route-bound in the runtime layer.

## 3. Database & State Audit
- Access control is real and relatively simple. The entry path reads `user_subscriptions` and `user_global_stats` through [`src/lib/admin/get-admin-profile.ts`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/lib/admin/get-admin-profile.ts), and it resolves dev gating from a cookie in [`src/lib/admin/feature-flags.ts`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/lib/admin/feature-flags.ts). This part of the feature is not the source of the layout failure.
- The codebase does have a real 3D Lab persistence model, but the visible runtime bypasses it. `DATABASE_SCHEMA.sql` defines `spatial_hotspots`, and [`src/lib/actions/lab.ts`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/lib/actions/lab.ts) can load model rows plus hotspots and record session interactions. The current query-param viewer uses static TypeScript registry/config imports instead, so there is no live connection between hotspot data, session state, and the rendered shell.
- State ownership is fragmented across at least three layers. [`src/stores/useLabStore.ts`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/stores/useLabStore.ts) manages viewer progress and quiz state, [`src/app/dashboard/3d-lab/_stores/labStore.ts`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/app/dashboard/3d-lab/_stores/labStore.ts) still manages parametric invalidation and hotspot state for older scenes, and [`src/features/wall-configurator/store/useWallConfigStore.ts`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/wall-configurator/store/useWallConfigStore.ts) owns the standalone wall wizard. There is no single authoritative shell store.
- Even the promoted feature hooks still depend on route-private state. [`src/features/3d-lab/hooks/useInvalidateOnChange.ts`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/3d-lab/hooks/useInvalidateOnChange.ts) imports the route-private lab store, so the feature package is still coupled to app-level implementation detail.
- Telemetry is largely inert. [`src/features/3d-lab/components/ModuleViewer.tsx`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/features/3d-lab/components/ModuleViewer.tsx) instantiates [`src/hooks/useLabTelemetry.ts`](/C:/Users/Philip%20Lewis/Desktop/slatecamp/src/hooks/useLabTelemetry.ts), but the hook's interaction recorders are not wired into hotspot clicks, zooms, or orbit controls. In practice, the analytics contract is present in code but not in the live user flow.
- Local state currently carries UX semantics that should be product state. Onboarding and module-seen behavior rely on `localStorage` keys, which is fine for purely local affordances, but those same local values are currently standing in for real module progress and shell context.

# Implementation Plan
## Phase 1: Layout & Routing Resolution
1. Canonicalize the route contract. Keep `/dashboard/3d-lab` as the browser page and introduce a single module-detail route, preferably `/dashboard/3d-lab/[moduleId]`. Redirect legacy `?model=` URLs and `/dashboard/3d-lab/wall-configurator` into that canonical route so cards, sidebar links, admin deep links, and future breadcrumbs all resolve to one shape.
2. Move the persistent canvas out of `src/app/dashboard/3d-lab/layout.tsx` and into a viewer-only shell component. The browser page should not mount WebGL, and the viewer should fill the available dashboard content region rather than the full viewport.
3. Replace the current "standalone viewer inside a shared shell" assumption with an explicit `LabModulePage` contract: inherited dashboard sidebar/header stay intact, while the module page owns only its internal toolbar, viewport, overlays, and module metadata.
4. Centralize navigation in a single 3D Lab route helper. `dashboard-visibility.ts`, sidebar children, module cards, and admin model links should all generate URLs from the same function so route drift cannot recur.
5. Add smoke verification for the four dashboard-visible modules: browser view renders with dashboard chrome, module view preserves sidebar/header, back navigation returns to the browser, and redirects normalize all legacy entry points.

## Phase 2: Component Containerization & Modularization
1. Create a feature-owned shell layer under `src/features/3d-lab/components/shell` with shared containers such as `LabBrowserShell`, `LabModuleShell`, `LabViewportFrame`, `LabOverlayLayer`, `LabMetaPanel`, and `LabEmptyState`.
2. Refactor `LabTopBar`, `ModuleContextCard`, `InfoPanel`, and `OnboardingFlow` onto shared shell primitives and remove inline style ownership from those components.
3. Finish the feature extraction. Move remaining `_templates`, `_scenes`, `_hooks`, and `_stores` behind feature-owned adapters, then delete dead route-private duplicates once imports are updated.
4. Treat Storybook as part of the componentization definition of done. Every time a 3D Lab UI component is extracted, renamed, materially restyled, or moved behind a new shell or container boundary, add or update the corresponding stories in `src/features/3d-lab/components/*.stories.tsx` or `src/storybook/scenes/**/*`, plus any required fixtures, mocks, and decorators in `src/storybook/*`, in the same change set.
5. Unify state boundaries. Keep one shell-level lab store for viewer/session metadata, and let template-specific or module-specific state live behind separate adapters. Retire one of the two competing `useLabStore` contracts.
6. Replace the synthetic module metadata shim with real module data. The shell should receive actual title, code reference, hotspot counts, estimates, and progress from the registry or from a server loader, not from hardcoded placeholders.
7. Decide on one content source of truth for hotspot-driven modules. Either wire the live runtime to `get3DModuleBySlug`, `create3DLabSession`, and `record3DLabInteraction`, or remove those contracts and formalize static registry/config files as the only source. The current mixed model is the worst state because both sides exist and neither is authoritative.
8. Bring the wall configurator into the same shell contract. It can keep its specialized computation flow, but it should stop presenting itself as a separate product with a separate page header and page-height strategy.

## Phase 3: Typographic & Visual Hierarchy Standardization
1. Define a 3D Lab type scale and token map before touching individual components: eyebrow, module title, section title, body copy, metadata, button label, and numeric/meta mono styles.
2. Replace hardcoded hex colors and inline typography in browser and shell components with Campfire semantic tokens. This includes `LabBrowser`, `CategoryGrid`, `ModuleList`, `LabTopBar`, `ModuleContextCard`, `InfoPanel`, `OnboardingFlow`, and the wall configurator step components.
3. Normalize panel widths, corner radii, shadows, spacing increments, and overlay offsets across all templates so every module feels like a variation within one system rather than a different product.
4. Standardize information architecture inside the module shell: module identity first, instructional context second, interaction controls third, assessment or telemetry affordances last.
5. Add visual coverage for the shared shell components in Storybook and use that as the enforcement layer for future typography and token regressions. This should include shared shell primitives, key overlay states, and module variants so visual hierarchy changes are reviewed in isolation instead of only through the live route.
6. Run final QA against desktop and mobile breakpoints, reduced-motion behavior, keyboard dismissal, focus handling, and contrast. The goal is not just visual consistency but a predictable interaction model across all four visible modules.
