# Slatecamp Project Context

This is the project-local operating guide for Hermes when working inside the Slatecamp repository.

## First Rule

Do not assume the stack, architecture, commands, deployment target, or product details until you inspect the repository. Use live files and current Git state as the source of truth.

## Startup Orientation

At the start of a Slatecamp session, inspect in this order when relevant:

1. `.ai/` folder for existing AI context, goals, known issues, workflows, and project notes.
2. Root README and docs.
3. Current Git status, branch, and recent history.
4. Package manifests, lockfiles, build/test configs, deployment configs, and environment examples.
5. Source tree, entry points, routes, components, services, state/data layers, and tests.

## `.ai` Folder Rule

Treat `.ai` as a knowledge base, not as unquestionable truth. Verify its claims against current code and Git history. If it is stale, report the mismatch clearly.

## Work Modes

### Orientation mode

Read only. Produce a Codebase Orientation Report. Do not modify files.

### Implementation mode

Make the smallest safe change. Preserve existing conventions. Run the relevant repo-native checks. Report files changed, commands run, results, risks, and next action.

### Review mode

Focus on correctness, security, product behavior, maintainability, performance, and test coverage. Prioritize issues that can actually break the product or create future maintenance cost.

## Safety

- Check Git status before editing.
- Avoid touching unrelated files.
- Do not expose secrets or private data.
- Do not alter production, auth, database, or deployment behavior without explicit user direction and a verification plan.
- Prefer reversible changes.
- Use exact file paths in summaries.

## Response Standard

Be concise and evidence-based. Include file paths, commands run, and remaining uncertainty. Avoid generic advice when repository evidence exists.
