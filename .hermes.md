# Slatecamp Project Context

This is the project-local control file for Hermes inside the Slatecamp repository.

Operate locally. Do not use or require a global `~/.hermes` setup unless the user explicitly asks for it. The active Slatecamp Hermes system lives in the local repository folder:

`.hermes/`

The primary AI knowledge layer lives in:

`.ai/`

Also inspect other local agent/system folders when relevant:

`.codex/`
`.omx/`
`.cursor/`
`.claude/`
`.gemini/`
`.github/`

---

## 0. Root Rule

Do not assume where the shell is.

Before giving shell commands, infer the current directory from the prompt or verify with `pwd`.

If the user is already inside the Slatecamp repo, do not tell them to `cd` into Slatecamp.

If the user is inside:

`.hermes/`

then the repo root is:

`../`

If the user is inside the repo root, the local Hermes folder is:

`.hermes/`

Never accidentally reference:

`.hermes/.hermes/`

That path is wrong unless it actually exists.

- product intent

- previous audits
- known issues
- workflows
- agent instructions
- prompt systems

- design decisions

Always validate `.ai/` claims against:

- current Git branch
- recent commits

## 8. Work Modes

### Orientation Mode

Use when the user asks to understand, audit, inspect, summarize, or diagnose.

Rules:

- read-only
- inspect `.ai/`, `.hermes/`, `.codex/`, `.omx/` when relevant
- inspect Git state
- inspect actual code
- produce a clear orientation report
- do not modify files

Output should include:

- what was inspected
- what the system appears to be
- key files/folders
- active branch/state
- risks or inconsistencies
- recommended next move

---

### Implementation Mode

Use when the user asks to build, fix, refactor, update, wire, generate, or change something.

Rules:

- check Git status before editing
- inspect `.ai/` first for intent
- inspect `.hermes/` for guardrails/checklists
- inspect `.codex/` and `.omx/` for related prior work
- make the smallest safe change
- preserve existing conventions
- avoid unrelated edits
- run repo-native checks when practical
- report exact files changed

Implementation priority:

1. correct behavior
2. minimal surface area
3. architectural consistency
4. reversibility
5. maintainability
6. performance
7. polish

Do not invent new architecture unless the current architecture is clearly insufficient.

---

### Review Mode

Use when the user asks to review, critique, audit, debug, or evaluate.

Focus on:

- correctness
- product behavior
- broken assumptions
- security
- data flow
- architecture drift
- performance
- maintainability
- test coverage
- deployment risk

Do not give generic feedback. Tie every point to concrete files, code, commands, or repository evidence.

Prioritize issues that can break the product or create future maintenance cost.

---

### Planning Mode

Use when the user asks for a plan, roadmap, sequence, migration, refactor strategy, or system design.

Rules:

- inspect `.ai/` first
- inspect existing architecture before proposing changes
- avoid speculative plans detached from the repo
- sequence work into reversible steps
- identify dependencies and risks
- define validation checks

A good plan should be executable by an agent without re-asking basic questions.

---

### Debug Mode

Use when something is broken.

Rules:

- reproduce or identify the failure first
- inspect logs, stack traces, configs, recent changes, and Git diff
- avoid random fixes
- isolate cause before patching
- prefer one fix at a time
- verify after change

Debugging order:

1. exact error
2. current directory
3. Git status
4. relevant `.ai/` notes
5. relevant `.hermes/` guardrails
6. recent changes
7. failing file/config
8. minimal fix
9. verification

## 9. Command Discipline

Before giving or running commands:

- account for the current directory
- avoid unnecessary `cd`
- use relative paths correctly
- quote paths when needed
- avoid destructive commands
- avoid overwriting files unless intended
- prefer `cp -n`, `mv -n`, or backups for uncertain changes
- never expose secrets
- never assume package manager; inspect lockfiles first

If the prompt shows:

`~/slatecamp/.hermes`

then commands targeting repo root files should usually use:

`../`

Examples:

- root `.hermes.md` from inside `.hermes/` is `../.hermes.md`
- local Hermes docs from inside `.hermes/` are `docs/`
- `.ai/` from inside `.hermes/` is `../.ai/`

If the prompt shows:

`~/slatecamp`

then commands should usually use:

`.hermes/`
`.ai/`
`.codex/`
`.omx/`

Do not give commands that assume the wrong directory.

## 10. Safety Rules

Always:

- check Git status before modifying files
- avoid unrelated edits
- preserve existing naming and structure
- prefer reversible changes
- use exact file paths in summaries
- separate facts from assumptions
- report uncertainty clearly
- validate with available checks
- protect secrets and private data

Never:

- modify production, auth, database, billing, deployment, or environment behavior casually
- delete files without explicit user intent
- overwrite user work without checking Git status
- invent missing files/folders
- pretend a command was run if it was not
- claim certainty without evidence
- skip `.ai/` for system-level decisions

## 16. Anti-Failure Rules

If you are about to act and have not checked `.ai/` for a Slatecamp system-level task, stop and check it.

If you are about to edit and have not checked Git status, stop and check it.

If you are about to give a shell command and have not accounted for the current directory, stop and correct the path.

If you are about to recommend global Hermes setup, stop. This Slatecamp setup is local-first unless the user explicitly asks otherwise.

If you are about to create duplicate instructions in multiple folders, stop and choose the smallest authoritative surface.

If you are about to make a broad architectural claim without reading code, stop and inspect the repo.
